# 验收与质量门禁

每个迭代只验证本迭代授权范围。先执行定向验证，再执行受影响模块验证，最后执行必要的项目级门禁；未定位根因前不得反复运行完整总门禁。

## 1. 基础门禁

每个迭代完成前至少检查：

1. 核心需求验收用例。
2. 受影响 Go 单元测试。
3. 必要的 Repository Integration Test。
4. OpenAPI 与 JSON Schema 契约校验。
5. Web 逻辑测试、Lint 和 TypeScript Typecheck。
6. 受影响范围的 Playwright E2E。
7. 数据库增量 Migration 与最终一致性检查。
8. `git diff --check`。
9. 文档和 `.ai-dev` 状态更新。
10. 工作区状态和提交范围正确。

前端生产构建、Docker 健康检查和更大范围回归根据迭代影响执行。执行记录必须写清具体命令，不得把尚未实现的占位命令记录为有效门禁。

## 2. 唯一数据库门禁

数据库相关门禁只作用于当前唯一数据库：

```text
ai_content_factory
```

必须验证：

1. 当前连接的数据库名称为 `ai_content_factory`。
2. 只执行尚未执行的增量 Migration。
3. 已冻结的历史 Migration 文件未被修改。
4. 当前 Migration Head 与本迭代预期一致。
5. 新增表、字段、索引、外键和唯一约束存在且定义正确。
6. 历史业务数据仍可读取。
7. 幂等操作没有产生重复记录。
8. 失败操作没有产生非法半成品数据。
9. 章节、正文、审核和重写等领域关系保持一致。
10. 所有检查均为非破坏性操作。

不得将以下操作作为常规测试或验收步骤：

- 创建独立测试数据库或验收数据库
- 空库全量重建
- `DROP DATABASE`
- `DROP SCHEMA`
- 全库 `TRUNCATE`
- Migration Down
- 修改历史 Migration 以匹配当前结构
- `docker compose down -v`

缺少数据库连接、数据库名称错误或 Migration 状态异常时，数据库门禁必须失败或明确标记未执行，不能记录为 PASS。

## 3. 验收边界

必须分别记录：

- 单元和 Repository 测试结果。
- API 契约结果。
- 浏览器 UI 验收结果。
- Mock 回归结果。
- 真实 n8n 联调结果。
- 真实 LLM 调用结果。
- 数据库最终一致性结果。

Iteration 15～18 浏览器 UI 验收通过，只代表对应页面和 UI 链路通过，不代表真实 n8n、真实 LLM或第二用户闭环最终验收已经完成。

## 4. 不接受的验收方式

- 只验证页面能打开。
- 只验证 HTTP 200。
- 使用前端 Mock 代替真实 API 验收。
- 使用确定性工作流结果宣称真实 LLM 已打通。
- 未验证刷新后的持久化状态。
- 未验证失败分支的数据库状态。
- 必要测试被 Skip 后仍宣称完整门禁通过。
- 验收后修改业务代码却不重新验证受影响范围。
- 把不同 Commit 上的代码、截图和测试结果组合成同一个最终 PASS。
